# 📚 Основы Разработки: От Файлов До Деплоя

Этот гайд объясняет базовые концепции разработки, которые помогут вам понять структуру проектов и процесс их публикации.

## 📖 Глоссарий для Новичков

**Если вы первый раз слышите эти термины - начните отсюда!**

### Git и Работа с Кодом

**Git** - система контроля версий. Помогает отслеживать изменения в коде и работать в команде.

**Репозиторий (repo)** - папка с проектом, которая отслеживается Git. Думайте о ней как о "хранилище кода".
```
Пример: ваш проект my-app - это репозиторий
```

**Коммит (commit)** - сохранение изменений в Git с описанием что вы сделали.
```
Аналогия: как сохранение игры с пометкой "прошёл 3 уровень"
Команда: git commit -m "Добавил кнопку входа"
```

**Пушить (push)** - отправить свои коммиты на удалённый сервер (GitHub, GitLab).
```
Простыми словами: загрузить код на GitHub
Команда: git push
Аналогия: как загрузить фото в облако
```

**Пулить (pull)** - скачать изменения с удалённого сервера к себе.
```
Простыми словами: скачать последнюю версию кода
Команда: git pull
```

**Клонировать (clone)** - скачать весь репозиторий себе на компьютер.
```
Команда: git clone https://github.com/user/project.git
```

**Ветка (branch)** - параллельная версия проекта для разработки новой фичи.
```
Пример: основной код в ветке main, новую фичу делаете в ветке feature-login
```

**Мёрджить (merge)** - объединить изменения из одной ветки в другую.
```
Пример: закончили фичу → мёрджите её в main
```

**Pull Request (PR)** - запрос на добавление ваших изменений в основной код.
```
Простыми словами: "Я сделал фичу, проверьте и добавьте в проект"
```

### Разработка и Запуск

**Деплоить (deploy)** - выложить приложение в интернет, чтобы пользователи могли им пользоваться.
```
Простыми словами: опубликовать сайт/приложение онлайн
До деплоя: работает только на вашем компьютере
После деплоя: доступно по ссылке всем в интернете
```

**Production (продакшн)** - рабочая версия приложения, которую используют реальные пользователи.
```
Пример: instagram.com - это production
```

**Development (разработка)** - версия для разработки на вашем компьютере.
```
Пример: localhost:3000 - это development
```

**Localhost** - ваш компьютер. Когда запускаете проект локально.
```
Пример: http://localhost:3000
Простыми словами: сайт работает только на вашем компьютере
```

**Build (билд)** - процесс преобразования кода в готовое приложение.
```
Команда: npm run build
Пример: из React компонентов создаются HTML/CSS/JS файлы
```

**Environment (окружение)** - настройки где запускается приложение.
```
Development окружение: на вашем компьютере
Production окружение: на сервере в интернете
```

### Архитектура Приложений

**Фронтенд (Frontend)** - то, что видит пользователь. Интерфейс, кнопки, дизайн.
```
Технологии: React, Vue, HTML, CSS, JavaScript
Простыми словами: красивая часть сайта
```

**Бэкенд (Backend)** - серверная часть. Логика, база данных, обработка запросов.
```
Технологии: Node.js, Python, Go
Простыми словами: то, что работает "за кулисами"
```

**Full-stack** - и фронтенд, и бэкенд вместе.
```
Full-stack разработчик: умеет делать и красивый интерфейс, и логику на сервере
```

**API (Application Programming Interface)** - способ общения между программами.
```
Пример: ваш сайт запрашивает данные у сервера через API
GET /api/users → получить список пользователей
```

**REST API** - популярный стиль создания API.
```
GET /posts - получить посты
POST /posts - создать пост
PUT /posts/1 - обновить пост
DELETE /posts/1 - удалить пост
```

**Database (БД, База данных)** - место хранения данных приложения.
```
Примеры: PostgreSQL, MySQL, MongoDB
Простыми словами: как Excel таблица, но для приложений
```

### Инструменты и Технологии

**npm (Node Package Manager)** - менеджер пакетов для JavaScript. Устанавливает библиотеки.
```
Команда: npm install express
Простыми словами: магазин готовых решений для кода
```

**Package (пакет)** - готовая библиотека кода, которую можно установить.
```
Пример: express - пакет для создания веб-серверов
```

**Dependencies (зависимости)** - пакеты, которые нужны вашему проекту.
```
В package.json указаны все зависимости
npm install - установит все сразу
```

**CLI (Command Line Interface)** - программа управляется через текстовые команды.
```
Пример: git, npm - это CLI инструменты
Противоположность: GUI (графический интерфейс с кнопками)
```

**Framework (фреймворк)** - готовая структура для разработки приложений.
```
Примеры: Next.js, Express.js, Django
Простыми словами: готовый "скелет" приложения
```

**Library (библиотека)** - набор готовых функций для решения задач.
```
Примеры: React, lodash
Отличие от фреймворка: библиотека - инструмент, фреймворк - готовая структура
```

### DevOps и Инфраструктура

**Server (сервер)** - компьютер в интернете, где работает ваше приложение.
```
VPS, Cloud Server, Dedicated Server - разные типы серверов
```

**VPS (Virtual Private Server)** - виртуальный сервер в облаке.
```
Примеры: DigitalOcean Droplet, AWS EC2
Простыми словами: арендованный компьютер в интернете
```

**Docker** - технология для упаковки приложения со всеми зависимостями.
```
Простыми словами: контейнер с вашим приложением, который работает везде одинаково
```

**Container (контейнер)** - изолированная среда для запуска приложения.
```
Аналогия: как посылка с приложением, которая откроется на любом сервере
```

**CI/CD (Continuous Integration/Deployment)** - автоматическая проверка и деплой кода.
```
Пример: запушили код → автоматически тесты → автоматический деплой
```

**SSH (Secure Shell)** - защищённое подключение к серверу.
```
Команда: ssh user@server.com
Простыми словами: удалённое управление сервером
```

**Domain (домен)** - адрес сайта в интернете.
```
Примеры: google.com, github.com
Вместо IP адреса (192.168.1.1) используется понятное имя
```

**DNS** - система преобразования доменов в IP адреса.
```
Простыми словами: телефонная книга интернета
mysite.com → 104.26.13.45
```

## 📁 Часть 1: Основные Файлы в Проектах

### `.env` - Файл с Секретами

**Что это?**
Файл с переменными окружения (environment variables) - настройками и секретными данными вашего приложения.

**Пример `.env` файла:**

```env
# База данных
DATABASE_URL=postgresql://user:password@localhost:5432/mydb

# API ключи
OPENAI_API_KEY=sk-proj-abc123def456...
STRIPE_SECRET_KEY=sk_test_xyz789...

# Настройки приложения
PORT=3000
NODE_ENV=development

# Сторонние сервисы
SENDGRID_API_KEY=SG.abc123...
AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG...
```

**ПОЧЕМУ НЕЛЬЗЯ ПУШИТЬ .env В GIT?**

1. **Безопасность**: В `.env` хранятся пароли, API ключи, токены
2. **Конфиденциальность**: Если репозиторий публичный, все увидят ваши секреты
3. **Разные окружения**: У каждого разработчика и на сервере свои настройки

**Реальная история:**
```
Разработчик запушил .env с ключами AWS в GitHub
→ Боты нашли ключи за 5 минут
→ Накрутили $5000 на его аккаунте за ночь
→ Amazon прислал счёт на оплату
```

**Что делать?**
1. Добавить `.env` в `.gitignore`
2. Создать `.env.example` с пустыми значениями
3. Документировать какие переменные нужны

**Пример `.env.example`:**
```env
# База данных
DATABASE_URL=

# API ключи (получить на https://platform.openai.com)
OPENAI_API_KEY=

# Настройки приложения
PORT=3000
NODE_ENV=development
```

### `.gitignore` - Что НЕ Отправлять в Git

**Что это?**
Файл, который говорит Git игнорировать определённые файлы и папки.

**Зачем нужен?**
- Не пушить секреты (`.env`)
- Не загружать зависимости (`node_modules/`) - они огромные
- Не версионировать временные файлы
- Не пушить личные настройки IDE

**Типичный `.gitignore` для Node.js:**

```gitignore
# Зависимости (можно установить через npm install)
node_modules/

# Секреты (НИКОГДА не пушить!)
.env
.env.local
.env.*.local

# Логи
*.log
npm-debug.log*

# IDE (у каждого свои настройки)
.vscode/
.idea/
*.swp

# ОС файлы
.DS_Store
Thumbs.db

# Билды (генерируются автоматически)
dist/
build/
.next/

# Кэши
.cache/
.parcel-cache/
```

**Почему `node_modules/` в .gitignore?**
- Может весить 100-500 МБ
- Можно восстановить командой `npm install`
- Разные версии для разных ОС
- Загрязняет историю коммитов

### Другие Важные Файлы

#### `package.json` и `package-lock.json`

**package.json** - манифест проекта:
```json
{
  "name": "my-app",
  "version": "1.0.0",
  "dependencies": {
    "express": "^4.18.0",
    "react": "^18.0.0"
  }
}
```

**package-lock.json** - точные версии всех зависимостей:
- Гарантирует одинаковые версии у всех
- НУЖНО пушить в git
- Генерируется автоматически

#### `README.md`

Первое, что видят люди в вашем проекте:
- Что делает проект
- Как установить
- Как использовать
- Примеры

#### `docker-compose.yml` (для сложных проектов)

Описывает сервисы приложения:
```yaml
services:
  app:
    build: .
    ports:
      - "3000:3000"
  db:
    image: postgres:15
```

## 🏗️ Часть 2: Типичный Функционал Приложений

Почти в каждом приложении есть стандартные фичи. Понимая их, вы сможете быстрее разрабатывать и лучше общаться с ИИ.

### Основные Модули Приложений

#### 1. **Аутентификация (Authentication)**

**Что это?** Проверка, кто вы ("Вы действительно Иван?")

**Стандартный функционал:**
- Регистрация (Sign Up)
- Вход (Sign In / Login)
- Выход (Logout)
- Восстановление пароля (Password Reset)
- Подтверждение email
- Social login (Google, GitHub, etc.)

**Пример промпта для ИИ:**
```
"Создай систему аутентификации с:
- Регистрацией через email/пароль
- Подтверждением email
- JWT токенами
- Refresh tokens для автоматического продления сессии"
```

#### 2. **Авторизация (Authorization)**

**Что это?** Проверка, что вам можно делать ("Можете ли вы удалить этот пост?")

**Стандартный функционал:**
- Роли (Admin, User, Moderator)
- Права доступа (Permissions)
- Проверка владения ресурсом

**Типичные роли:**
```
Admin → может всё
Moderator → может модерировать контент
User → может управлять своим контентом
Guest → только просмотр
```

#### 3. **Онбординг (Onboarding)**

**Что это?** Знакомство нового пользователя с приложением

**Типичные шаги:**
1. Приветственный экран
2. Заполнение профиля
3. Выбор интересов/настроек
4. Туториал/подсказки
5. Первое действие (создать пост, добавить друга)

#### 4. **Профиль Пользователя**

**Стандартные элементы:**
- Аватар
- Имя, био
- Email (часто скрытый)
- Настройки приватности
- История активности
- Статистика

**Настройки профиля:**
- Редактирование данных
- Смена пароля
- Настройки уведомлений
- Удаление аккаунта

#### 5. **CRUD операции** (Create, Read, Update, Delete)

Основа почти всех приложений - создавать, читать, обновлять, удалять данные.

**Примеры:**
- **Blog:** создать пост, прочитать, отредактировать, удалить
- **E-commerce:** добавить товар в корзину, просмотреть, изменить количество, удалить
- **Social media:** создать пост, смотреть ленту, отредактировать, удалить

#### 6. **Поиск и Фильтрация**

- Поиск по тексту
- Фильтры (категории, даты, цены)
- Сортировка (по дате, популярности, цене)
- Пагинация (разбивка на страницы)

#### 7. **Уведомления**

**Типы:**
- Push уведомления (в браузере/телефоне)
- Email уведомления
- In-app уведомления (внутри приложения)
- SMS (реже)

#### 8. **Работа с Файлами**

- Загрузка файлов (Upload)
- Хранение (локально/облако)
- Обработка (ресайз картинок, сжатие)
- Скачивание (Download)

#### 9. **Аналитика и Метрики**

- Количество пользователей
- Активность
- Популярные действия
- Конверсии

## 🗄️ Часть 3: Базы Данных - Когда Что Использовать

### Локальная БД vs Облачная БД

#### Локальная БД (SQLite, PostgreSQL на машине)

**Когда использовать:**
- Разработка и тестирование
- Обучение
- Небольшие personal проекты
- Десктоп приложения
- Нужна скорость работы без интернета

**Плюсы:**
- Быстрая
- Бесплатная
- Полный контроль
- Работает без интернета

**Минусы:**
- Сложно масштабировать
- Нужно делать бэкапы вручную
- Доступна только на одной машине

**Пример (SQLite):**
```javascript
// Один файл database.db на диске
const db = new SQLite('database.db');
```

---

#### Supabase / Firebase / PlanetScale (Облачные БД)

**Что такое Supabase?**
- PostgreSQL база данных в облаке
- + Auth (аутентификация)
- + Storage (хранилище файлов)
- + Realtime (обновления в реальном времени)
- + Edge Functions

### Supabase: Локально vs Облако

#### Supabase Локально (Self-hosted)

**Когда использовать:**
- У вас есть свой сервер
- Нужен полный контроль
- Требования безопасности/комплаенс
- Большой проект с много данных

**Как запустить:**
```bash
# Через Docker
npx supabase init
npx supabase start
```

**Плюсы:**
- Бесплатно (платите только за сервер)
- Полный контроль
- Данные у вас

**Минусы:**
- Нужно настраивать сервер
- Сами делаете бэкапы
- Сами следите за безопасностью
- Нужны навыки DevOps

---

#### Supabase Cloud (Облачная версия)

**Когда использовать:**
- Быстрый старт проекта
- MVP / прототип
- Малые и средние проекты
- Не хотите заниматься инфраструктурой
- Нужна надёжность из коробки

**Плюсы:**
- Запуск за 2 минуты
- Автоматические бэкапы
- Масштабирование
- Мониторинг и логи
- Бесплатный тир (до 500 МБ БД, 2GB storage)

**Минусы:**
- Платно при росте
- Зависимость от сервиса
- Меньше контроля

**Примерная стоимость:**
```
Free: до 500 МБ БД, 1 GB storage
Pro: $25/месяц - 8 GB БД, 100 GB storage
Team: от $599/месяц
```

---

### Таблица Выбора БД

| Сценарий | Рекомендация |
|----------|-------------|
| Учебный проект | SQLite локально |
| Прототип/MVP | Supabase Cloud (Free tier) |
| Telegram бот (мало данных) | SQLite или Supabase Free |
| SaaS стартап | Supabase Cloud (Pro) |
| Корпоративное приложение | PostgreSQL на своём сервере или Supabase Self-hosted |
| Мобильное приложение | Supabase Cloud или Firebase |
| Offline-first приложение | SQLite + синхронизация |

## 🚀 Часть 4: Гайд по Деплою

### Уровень 1: Простой Лендинг / Сайт с БД

**Проект:**
- Статический сайт
- Или простое приложение (React, Vue, Next.js)
- БД на Supabase
- Нет сложной бэкенд логики

**Решение 1: Lovable**

**Когда использовать:**
- Создаёте сайт прямо в браузере с помощью ИИ
- Нужен быстрый результат (часы, не дни)
- Не хотите разбираться с кодом

**Что умеет Lovable:**
- Генерирует React приложения по описанию
- Встроенный деплой
- Интеграция с Supabase

**Процесс:**
```
1. Описываете что нужно → Lovable генерирует код
2. Корректируете через чат
3. Нажимаете "Deploy" → сайт в продакшене
```

**Плюсы:**
- Очень быстро (минуты)
- Не нужно знать код
- Автоматический деплой

**Минусы:**
- Ограниченная кастомизация
- Зависимость от платформы
- Платный тариф для серьёзных проектов

---

**Решение 2: Vercel**

**Когда использовать:**
- Разрабатываете локально (VSCode)
- Используете Next.js, React, Vue
- Нужны serverless функции
- Хотите больше контроля

**Процесс:**
```bash
# 1. Разработка локально
npm create next-app my-app
cd my-app

# 2. Подключение к Vercel
npm install -g vercel
vercel login
vercel

# Всё! Сайт задеплоен
```

**Плюсы:**
- Git integration (push → автодеплой)
- Preview deployments (каждый PR = отдельный URL)
- Бесплатный тир очень щедрый
- Serverless functions
- Оптимизация из коробки

**Минусы:**
- Для сложной логики нужен отдельный бэкенд
- Ограничения на serverless функции

**Примерная стоимость:**
```
Hobby (Free): отлично для личных проектов
Pro ($20/месяц): для коммерческих проектов
```

### Уровень 2: Telegram Бот / Простой Бэкенд

**Проект:**
- Один модуль (бот, API, воркер)
- Нет фронтенда или он отдельно
- Простая архитектура

**Решение: Railway**

**Когда использовать:**
- Telegram бот
- Discord бот
- Background воркеры
- Простой REST API
- Scheduled tasks (cron jobs)

**Процесс:**
```bash
# 1. Код готов локально
# 2. Идём на railway.app
# 3. "New Project" → подключаем GitHub
# 4. Railway автоматически:
   - Определяет Node.js
   - Устанавливает зависимости
   - Запускает приложение
```

**Что круто в Railway:**
- Деплой за 3 клика
- Бесплатный тир ($5 кредитов/месяц)
- Встроенная PostgreSQL/Redis
- Логи в реальном времени
- Переменные окружения через UI
- Метрики из коробки

**Пример для Telegram бота:**
```javascript
// bot.js
const TelegramBot = require('node-telegram-bot-api');
const bot = new TelegramBot(process.env.TELEGRAM_TOKEN, {polling: true});

bot.on('message', (msg) => {
  bot.sendMessage(msg.chat.id, 'Привет!');
});

// Railway запустит это автоматически!
```

**Примерная стоимость:**
```
Trial: $5 кредитов/месяц (хватает для маленького бота)
Developer: $5-10/месяц (небольшие проекты)
Team: от $20/месяц
```

### Уровень 3: Сложная Архитектура

**Проект:**
- Несколько сервисов на бэкенде (микросервисы)
- Отдельный фронтенд
- Несколько баз данных
- Кэширование (Redis)
- Очереди сообщений

**Решение: Docker + Nginx (+ VPS/Cloud)**

**Когда это нужно:**
- Масштабируемое приложение
- Много пользователей
- Разные команды работают над разными сервисами
- Нужен полный контроль

**Что нужно знать:**
- Docker (контейнеризация)
- Nginx (reverse proxy, балансировка)
- Linux (работа с сервером)
- CI/CD (автоматический деплой)
- Мониторинг (что сломалось?)

**Пример архитектуры:**
```
                    ┌─────────────┐
Пользователь ──────>│    Nginx    │
                    │(reverse proxy)
                    └──────┬──────┘
                           │
           ┌───────────────┼───────────────┐
           │               │               │
      ┌────▼────┐     ┌────▼────┐    ┌────▼────┐
      │Frontend │     │ Backend │    │   API   │
      │ (React) │     │(Node.js)│    │ Service │
      └─────────┘     └────┬────┘    └────┬────┘
                           │              │
                      ┌────▼──────────────▼────┐
                      │   PostgreSQL + Redis   │
                      └────────────────────────┘
```

**Наш совет для новичков:**

**ПОКА НЕ ЛЕЗЬТЕ СЮДА САМОСТОЯТЕЛЬНО!**

Если ваш проект дорос до такого:
1. **Найдите DevOps инженера** - это отдельная специальность
2. **Или используйте готовые решения:**
   - Railway (умеет микросервисы)
   - Render (аналог Railway)
   - DigitalOcean App Platform (управляемый деплой)
   - Google Cloud Run (serverless контейнеры)

**Когда стоит изучить Docker:**
- У вас стабильный проект
- Нужна воспроизводимость (работает везде одинаково)
- Вы готовы потратить недели на изучение
- Вам интересна DevOps специализация
